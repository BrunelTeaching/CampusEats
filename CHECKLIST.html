CS3616 Coursework — Checklist

0 Setup — get your file and your agent Before you start

Do all of this once, before you touch any code. You are aiming to reach a known-good starting line: the suite green, the tools installed, your file identified, and an agent that responds.

  • Clone the repo and work in your local clone. You never push — the local .git folder is your evidence trail.
  • Create the environment and confirm the suite is green on the untouched code: 
    python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
pytest -q          # must pass before you change anything
  • Find your assigned file. It is assigned by your student registration number (mod 6) — see the allocation page on Brightspace. You do not choose it. Open your file and read it before prompting anything.
  • Have one agent working. Use the one you set up in the Week 2 lab:
Agent A — GitHub Copilot

Free, with Copilot Pro free for students via the GitHub Student Developer Pack (verify with your Brunel email at github.com/education). Use it in VS Code Agent mode, or as a terminal agent:

Agent B — OpenCode + a free Gemini Flash model

Install OpenCode, then inside it run /models, pick a Google Gemini Flash model, and paste a free API key from aistudio.google.com/apikey.

Export every session as you go. Each time you finish a working session with your agent, export the transcript and save it in the agent_logs/ folder — see step 4 for how. On model tier. If you use Claude Code or Codex, pick a lower-tier model on purpose — its weaker output makes exactly the mistakes you are here to catch. Top-tier models overstretch (fixing a bug you were told to leave, refactoring past the plan), which is harder to spot because it looks polished. Either way, you own every change the agent makes.

1 Diagnose — run the tools Compulsory

Run the three core tools (ruff, radon, pytest-cov) on your assigned file — you already know the commands from the labs. The one thing to get right here is saving each run into a before/ folder: the saved file, not the number you type into the table later, is what a marker re-runs. Redirect the output with >, and add 2>&1 so findings are captured even when the tool exits non-zero. For example:

mkdir before
ruff check campuseats/your_file.py > before/ruff.txt 2>&1

Do the same for the other two tools, and later into an after/ folder once you have refactored.

  • Write a short diagnosis of your file — this is the raw material for §2 of your report. Keep it to a few sentences:
    • one sentence on what the tool output flags;
    • two or three sentences of your own observations from reading the file;
    • one or two sentences on what your LLM interactions turned up, and the prompts you used (if any).
2 Refactor — direct the agent, iteratively Compulsory

This is the core of the task and it is iterative: prompt, read the result, re-run a tool, correct the agent, commit, repeat. You are steering — not accepting the first thing it writes.

  • Read your file and the relevant lecture (SOLID / SRP, DRY, coupling & cohesion, clean naming, dead code). Your §2 analysis must name real principles, not symptoms.
  • Design your prompts from the evidence in step 1 and your own reading of the file — e.g. "radon reports complexity 12 in priced_order; extract the member and promo blocks into named functions, keep behaviour identical."
  • Aim for 3 distinct, named refactorings (Extract Method, Remove Duplication, Rename, Remove Dead Code…), each traceable to one line of your plan. Up to 4 is fine; fewer only if staff-agreed.
  • Commit to git after every refactoring — one commit per change, so your history lines up with your plan item by item. This is required evidence: your .git folder must show at least one commit per refactoring (so two or more in total). Do it as you go — you cannot reconstruct it afterwards.
  • Stay behaviour-preserving. The suite must pass, asserting the same things, after every change. Found a real bug? Note it in §2 and leave it alone — this is refactoring, not bug-fixing.
  • Catch the agent. You need at least one genuine mistake in §3 — and the agent will not hand it to you. The hints below are where they hide.
How to catch the agent out — where mistakes hide
  • Inspect the diff, not just the numbers. Some mistakes never show up in a tool count: a warning "fixed" by adding # noqa (silencing it, not fixing it), a function quietly deleted, behaviour subtly changed. Read git diff line by line.
  • Run mypy on your file (before and after). A classic agent move is "adding type hints" that actually introduce new type errors — and because mypy is easy to skip, nobody notices. The error count should go down, not up.
  • Re-run every tool yourself, after refactoring. Do not trust the numbers the agent reports — it frequently misreports them or never re-ran the tool at all. The saved after/ file must be your run.
  • Run the full test suite (pytest), not just your own file's tests. Agents often verify a subset and miss breakage elsewhere.
  • Verify "dead code removed" is really dead. Search the codebase for callers (grep -rn "name" .) before trusting any deletion — something may still use it.
  • Ask why each metric moved. Coverage can rise just because code was deleted; a complexity number can fall because logic was dropped, not restructured. A number that improved for the wrong reason is a finding, not a win.
3 Re-measure & complete the report Compulsory
  • Capture the after/ numbers. Re-run the same tools into after/. At least one number must show a genuine, explained improvement — and pytest must still say all tests passed.
  • Fill in Submission.docx (the Word template — keep it to one page):
    • §1 Tools — the before/after table, each row pointing at its evidence file.
    • §2 Analysis — the named principles your file breaks and the refactorings you made.
    • §3 Reflection — how the agent did, with at least one real mistake and the evidence file that proves it.
  • Record the agent and model you used at the top of the form.

The bar to hold yourself to: could you convince your boss this refactored file is safe to ship to production? Your evidence is exactly what goes in the zip — the full test suite green (behaviour unchanged), the diff you have read line by line, every tool re-run with its before/after numbers, and any bug you found logged rather than quietly fixed. If you can't make that argument, the refactor isn't done.

4 Export, archive & submit Before you submit

Everything heavy goes in the zip, not in the report. Before you zip, walk the checklist below and then run the checker. If you have set up everything correctly, zipping your working folder should be enough.

What must be in your zip
  • The completed report — Submission.docx.
  • Your refactored file / class — the diff, or the full changed file(s).
  • Your before/ and after/ folders of tool output.
  • Your LLM session transcript — exported into the agent_logs/ folder (see "How to export your transcript" below).
  • The local .git folder — the folder itself, showing one commit per refactoring (at least 2 in total). Do not push it anywhere.
How to export your transcript into agent_logs/

Export your whole agent session and save it into the agent_logs/ folder before you zip. Do this at the end of your session — do not rely on memory.

GitHub Copilot (VS Code): open the Command Palette (Cmd/Ctrl+Shift+P), run “Chat: Export Chat…”, and save the .json into agent_logs/. (For the terminal copilot agent, copy the session text into agent_logs/copilot.txt.)

OpenCode + Gemini Flash: run opencode export and save the output into agent_logs/. Sessions are stored under ~/.local/share/opencode/ — run opencode db path if you need to locate them.

  • Run the checker inside your folder to confirm nothing is missing: 
    bash check_submission.sh
  • Zip and upload one file to WISEflow, named with your registration number (e.g. CS3616_0612345.zip). Confirm it uploaded fully with no errors — that is your responsibility.

The integrity line. Directed AI use is required and expected. What counts as misconduct here is misrepresenting the session: claiming a catch with no evidence file, overstating an improvement the numbers do not support, or presenting a struggling session as if it went smoothly. Declare your tool and model, and submit the transcript and git history as evidence.
